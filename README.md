# Dr.Clash

A fan-made companion web application for Clash of Clans. Dr.Clash provides a community-driven feature request and bug reporting board with voting, plus a landing page showcasing mobile app capabilities including upgrade tracking, base layouts, army planning, stats tools, mini-games, and home screen widgets.

The project consists of an **Angular frontend** (hosted on Vercel) and a **Cloudflare Workers API** backend with a D1 SQLite database.

---

## Purpose

Dr.Clash exists to serve as the companion web presence for a Clash of Clans mobile app. Its core interactive feature is a community voting board where users can submit feature requests and bug reports, upvote/downvote them, and track their resolution status. The website also acts as a marketing landing page to promote the mobile app across app stores.

The intended audience is Clash of Clans players who want to influence the app's development direction through community voting, and users evaluating the mobile app before downloading.

## Architecture

### High-Level Architecture

The application follows a **serverless JAMstack** architecture with a decoupled frontend and API.

### Request Flow

1. Browser loads the Angular SPA from Vercel.
2. Angular bootstraps the root `App` component with `NavComponent`, `FooterComponent`, and the `<router-outlet>`.
3. The router lazy-loads feature components based on the URL path.
4. Components that need data call `ApiService` methods, which use `fetch()` to hit the Cloudflare Workers API.
5. The Workers Hono app receives the request:
   - CORS headers are set, security headers applied.
   - JWT middleware verifies the Bearer token (if present) and attaches the user context.
   - Rate limiter middleware checks the request against D1 for auth/vote/post endpoints.
   - Route handler executes the business logic against D1 (read/write).
   - JSON response is returned.
6. Error responses from the API are caught by the services and surfaced in the UI via signals.

### Authentication Flow

```
┌──────────┐     ┌──────────────┐     ┌────────────────┐
│  User    │     │  Angular     │     │  Workers API   │
└────┬─────┘     └──────┬───────┘     └───────┬────────┘
     │                  │                      │
     │  Login/Register  │  POST /api/auth/*    │
     │─────────────────►│─────────────────────►│
     │                  │                      │
     │                  │    JWT + User JSON   │
     │                  │◄─────────────────────│
     │                  │                      │
     │                  │  Store token in      │
     │                  │  sessionStorage       │
     │                  │                      │
     │  Authenticated   │  Bearer token on     │
     │  Request         │  all subsequent calls │
     │─────────────────►│─────────────────────►│
     │                  │                      │  jwtVerify:
     │                  │                      │  decode + verify
     │                  │                      │  HS256 signature
     │                  │                      │
     │                  │  200/400/401/403     │
     │                  │◄─────────────────────│
```

- Session storage (`sessionStorage`) holds the JWT token.
- `AuthService` exposes a `user` signal (null | User) and a `loading` signal.
- On app init, `AuthService` checks for an existing token in sessionStorage and calls `/api/auth/me` to hydrate the user.
- Google OAuth redirects to the Workers callback, which exchanges the code for tokens, creates/links a user, and redirects back to the frontend with a JWT in the URL fragment.
- Logout clears sessionStorage and sets user to null.

### State Management

State is managed via **Angular signals** (`signal()` and `computed()`). There is no NgRx, Redux, or other external state library.

- `AuthService.user` — Current authenticated user (or null).
- `AuthService.loading` — Whether initial user load is in progress.
- `FeaturesBugComponent.posts` — Current post list, updated on filter/vote/create.
- Various UI signals (`showForm`, `submitting`, `expandedPosts`, etc.) are local to each component.

### Voting Logic

The voting system supports three states per user per post: upvote (+1), downvote (-1), or no vote (0/toggle). The logic handles:

- **New vote**: Insert vote row, increment upvotes by value.
- **Same vote (toggle off)**: Delete vote row, decrement upvotes by value.
- **Different vote (switch)**: Update vote value, increment upvotes by `value * 2` (e.g., switching from -1 to +1 adds 2 to upvotes).

Optimistic UI updates are applied: the local post array is updated immediately, then the server response corrects the count. On error, the previous state is restored.

### Rate Limiting

Each request is identified by a SHA-256 hash of the IP address (truncated to 16 hex chars) combined with the request path. The limiter uses D1's `ON CONFLICT` upsert to atomically increment a counter per time window. If the count exceeds the threshold, a `429 Too Many Requests` response is returned. If D1 is unavailable, the limiter fails open to avoid blocking legitimate traffic.

- **Strict limit** (auth endpoints): 10 requests per 60-second window.
- **Standard limit** (posts, votes): 30 requests per 60-second window.

### Data Lifecycle
- **Creating a post**: A user (authenticated, not admin) submits via `POST /api/posts`. Post is inserted with `status = 'current'` and `upvotes = 0`.
- **Voting**: Users toggle between upvote, downvote, and no vote. The `upvotes` column on `posts` is updated via arithmetic in SQL.
- **Resolution**: Admin marks posts as `done` or reopens them to `current`.
- **Replies**: Admin can reply to any post. Edits and deletes are supported.
- **Cleanup**: Admin can bulk-delete done posts (cascades to votes and replies).
- **Account deletion**: Removes user's votes, then votes on user's posts, then user's posts, then the user record.
- **Rate limits**: Expired rows remain in the table but are not queried for active windows. No cleanup mechanism is implemented in the codebase.

## How It Works

### User Flow

1. **Landing** — A visitor arrives at the home page. They see the Dr.Clash hero section with the app icon, a bold tagline ("Your Ultimate Tool for Clash of Clans"), and buttons linking to Google Play and the App Store. Six feature cards below explain the mobile app's capabilities.

2. **Browsing the Board** — The user navigates to `/features-bug`. The page loads the most popular open posts (features and bugs) sorted by upvotes. They can filter by All, Features, Bugs, or Done. Each post card shows the type badge, title, truncated content (with "Read more"), author, date, admin replies, and vote controls. Clicking "Load More" fetches the next page via cursor-based pagination.

3. **Voting** — To vote, the user must be logged in. They click `+` or `-` on a post. The count updates immediately (optimistic UI). If they click the same vote again, it toggles off. If they switch from upvote to downvote (or vice versa), the count adjusts by 2.

4. **Creating a Post** — An authenticated user clicks "+ Feature" or "+ Bug". A modal overlay appears with title and content fields. On submit, the post is created and appears at the top of the list.

5. **Authentication** — New users register with email, username, and password. Existing users log in. Alternatively, they can "Continue with Google" for OAuth. On success, a JWT token is stored in sessionStorage. The nav bar updates to show "Hello, {username}".

6. **Profile Management** — Clicking their username opens a profile modal where they can edit their display name or delete their entire account (with a two-step confirmation).

7. **Admin Flow** — An admin navigates to `/admin` and logs in with the admin credentials (defined in environment variables, not the users table). The admin dashboard shows a table of all posts with inline controls to mark as done, reopen, delete, reply (create/edit/delete), and a "Clear Done" button to bulk-remove completed posts.

8. **Password Reset** — A user who forgot their password clicks "Forgot password?" on the login page, enters their email, and receives a reset link via Resend (if the email is registered). The link contains a JWT token, expires in 1 hour, and directs to `/reset-password?token=...`.

9. **Google OAuth** — Clicking "Continue with Google" redirects to Google's consent screen. On success, Google redirects to the Workers callback, which exchanges the code for tokens, creates or links a user account, and redirects back to `/oauth-callback#token=...`. The callback component extracts the token, stores it, and navigates to the features board.

10. **Legal Pages** — `/privacy-policy` and `/terms-conditions` display legal content with scroll-triggered fade-up animations.
